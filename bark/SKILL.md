# bark

## Default stance

核心原则：
1. 一步到位：调 skill 目录下 `scripts/notify.py [选项] [标题] 正文` 即发；标题缺省
   「ZCode」，正文传 `-` 时从 stdin 读；全部选项以 `notify.py --help` 为准
   （--level/--group/--id/--url/--sound/--markdown/--ttl/--delete 等）。
2. 只在需要用户确认时推送（选项选择、裁决、阻塞性提问这类要用户拍板的情况）；
   任务完成不推送。标题=需要确认的问题（简洁），正文=问题描述（可读性强、自包含）；
   一个任务有多个待确认问题就发多条通知，一条一个问题。
3. `--group` 必带当前工作区名（如 `investment-dashboard`）。
4. 级别与痕迹按需选：默认亮屏即够；可稍后看的用 `--level passive`；必须立刻处理的用
   `--level critical`（可加 `--call`）；进度类推送复用同一 `--id` 避免刷屏；临时信息
   加 `--ttl` 或 `--no-archive` 不留痕。
5. 配置写死即约定：服务器与 device key 写死在脚本内（用户 2026-09-26 确认非敏感），
   不向用户索要，不改动，不外传给第三方服务。

禁止行为：
- 禁止无实质进展的连环推送；同一事件成功推送后不重发。
- 禁止把密钥、token、完整聊天记录等敏感内容放进正文——Bark 经公共服务器中转。
- 禁止用于给人发消息（那是 imsg 的职责）；本 skill 只推用户自己的 iPhone。

## Workflow

第一步 判定：有要用户确认/拍板的问题（选项选择、裁决、阻塞性提问），或用户显式点名
       通知；否则不推送——任务完成不发通知。
第二步 拟内容：标题=待确认问题本身（≤20 字、简洁），正文=该问题的可读描述；多个问题
       拆成多条通知依次执行；需要排版（加粗/列表/代码块）时用 `--markdown`；不塞密钥与全文。
第三步 执行：`python3 <skill目录>/scripts/notify.py --group <工作区名> [选项] "标题" "正文"`；
       多行/长正文走 stdin（第二个参数传 `-`），可按需加选项。
第四步 处置结果：退出码 0 即成功，向用户一句「已推送：<标题>」；非零读输出，网络类
       错误重试一次；返回 `code:400` 设备不存在说明 key 失效，如实报告，禁止擅自改
       key 或脚本。

## Output format

- 成功：`已推送：<标题>`（一句话，不贴完整 API 返回）。
- 失败：报告退出码与 API 返回体原文，不静默。

## 自检

- [ ] 标题=待确认问题（简洁）、正文=问题描述；多问题已拆成多条通知。
- [ ] 带了 `--group <工作区名>`；无敏感内容；级别/痕迹选项按需选。
- [ ] 已检查脚本退出码，失败已报告（未吞错、未擅自改配置）。
