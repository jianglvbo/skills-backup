# Default stance

## 核心认知：Skill 不是脚本，是认知架构

Skill ≠ 脚本（确定性执行）≠ 知识库（知道什么）≠ 工具（能做什么操作）
Skill = 任务编排者，决定何时、如何组织操作。

**Skill 是"数字员工入职培训手册"**——不是一次性对话设定，而是可持续演进的能力模块。

## 五层认知架构

Skill 的本质是为 AI 封装一种职业素养。每一层对应一个"器官"：

| 层级 | 对应结构 | 角色 | 职责 |
|:---|:---|:---|:---|
| 1. 元数据层 | YAML frontmatter | 社会身份 | "我是谁，我能解决什么问题" |
| 2. 指令层 | Markdown 正文 | 价值观与原则 | "我必须遵守哪些绝对底线" |
| 3. Reference（资源层-读取） | references/ | 长期记忆库 | "不需要时刻记着，但需要时精准检索" |
| 4. Script（资源层-执行） | scripts/ | 反射弧与手脚 | "不靠想象，直接干预和测量物理世界" |
| 5. 动态上下文 | 外部输入 | 感官神经 | "不被动响应，主动感知周遭环境" |

> 每层独立运行，层次越高效果越强。基础版只需 SKILL.md（1+2），进阶版逐步叠加。

## 分层执行（Hierarchical Execution）

Reference 让 AI "读"（消耗 Token），Script 让 AI "做"（消耗算力）。

- **认知卸载**：AI 上下文窗口 = 工作内存，极其昂贵。低频规则放到 Reference（外存），平时只带轻量索引，遇到模糊地带才精准翻阅。
- **执行优于模拟**：机械性验证、计算、文件操作，不要让 AI 在脑中模拟——直接派生子进程执行脚本，100% 准确 + 极省 Token。

## 核心原则
- 用模板写 Skill：6 段结构不可缺，缺了就补
- 主文件 ≤ 200 行：细节下沉 references/，不堆在主文件
- 确定性优先：编号清单 > 自然语言，决策树 > if-else 描述，脚本执行 > AI 模拟
- 规则有来源：不确定的标记 `[待验证]`
- **事前避免 > 事后自检（2026-09-11 用户硬约束，最高优先）**：约束要**前置到执行路径**，而不是靠事后检查弥补。落地顺序：
  1. **工具门禁**（最强）：能靠 API/脚本/DOM 校验拦截的，做成**硬门禁**，不合格数据**根本写不进去**（如服务端 `_validateSignal()` 拒收空泛信号）
  2. **执行步骤内置检查点**：写进 workflow 的**判定步骤**（如「第 1.5 步分流决策」内嵌三问），而不是最后的自检清单
  3. **正反例对照**：给出「❌ 不合格例 → ✅ 改写」对照表，让执行者在**动手前**就能比对
  4. **自检清单**：只兜底**无法自动化**的语义判断，不承担主要防错职责
  > **反面教材（2026-09-11）**：383 条信号误填、506 条 `—` 占位符、33 条 trade 缺方向——**全部是事后全库审查才发现**，说明设计时缺少事前门禁。事后修 291 条的成本远高于写入时拒绝 1 条。
  5. **真实提示词验证（2026-09-20 调研补齐）**：skill 交付前用 2–3 条带真实路径与口吻的提示词实际跑一遍——既测「该触发的触发」，也测「不该触发的不触发」，输出与执行 trace 和用户复盘（细则见 `references/testing.md`）。创建与重大修改都要过这步，静态自检不替代它——skill 的错误大多不在「写了什么」，而在「会不会触发、照不照做」。
- **Ai 仓库公共化（2026-08-31 用户确认）**：Ai 仓库 = 所有 agent 公用的公共 skill 仓库。设计 skill 时：① 不得含任何 agent 私有路径（`~/.workbuddy/`、`~/.qoderworkcn/` 等），统一用 `$HOME` 相对或通用约定（凭据放 `$HOME/.config/<skill>/`，0600）② 必要脚本/执行工具必须放 skill 目录 `scripts/` 或 `Ai/tools/`，skill 内用相对路径引用 ③ 敏感凭据/密钥不进仓库（只存本地 0600 文件或环境变量）

## 禁止行为
- 绝不把 Skill 写成百科文档（塞教科书常识）
- 绝不依赖模型自由发挥不确定步骤
- 绝不遗漏自检步骤
- 绝不让 AI 脑补机械性验证——能跑脚本就跑脚本
- **绝不把可自动化的校验只写成「自检」条目**——能做成门禁/脚本的必须前置（事前避免 > 事后自检）

# Workflow

## 创建新 Skill（四步递进）

每步都能独立运行，效果逐步增强：

### 第一步：SKILL.md 最小闭环
- 写 YAML frontmatter（name + description，这是 AI 选择 Skill 的唯一依据）
- 写指令正文（AI 的"条件反射"，遇到任务直接按肌肉记忆执行）
- 这步完成 = Skill 已经能跑

### 第二步：外挂 Reference（认知卸载）
- 把枚举值、规范表、低频规则从 SKILL.md 剥离
- 放入 references/，AI 按需精准检索
- 目标：主文件瘦身，AI 只带"索引"工作

### 第三步：接入 Script（执行优于模拟）
- 机械性验证（格式检查、数据校验、文件操作）写成脚本
- AI 不读脚本代码，只执行并读取输出
- 目标：100% 准确率 + 极省 Token

### 第四步：感知动态上下文
- 需要时注入外部环境信息（当前分支、暂存区状态等）
- AI 从"照本宣科"变为"因时因地制宜"

### 完整流程
1. 第一步：确定级别（轻量/标准/重量），见 `references/levels.md`
2. 第二步：填 YAML 门控——name、description 含触发词
3. 第三步：写 Default stance——最少 3 条核心原则 + 3 条禁止
4. 第四步：写 Workflow——第一步/第二步…编号，含决策点
5. 第五步：定 Output format——固定字段和类型
6. 第六步：列 Relative files——每个 references/ 写清何时加载（读/执行）
7. 第七步：填 Source hierarchy——优先级从用户约定到最佳实践
8. 第八步：加自检清单——最少 3 条
9. 第九步：真实提示词验证——写 2–3 条测试提示词（应触发 + 不应触发各占一半），实际触发验证 + 复盘输出与 trace，不过关回改；细则见 `references/testing.md`

## 修改已有 Skill

1. 第一步：改前先读——通读 SKILL.md 全文 + 相关 references + 脚本注释，定位旧规范残留；禁止只凭记忆改
2. 第二步：身份不动——保留原 name 与目录名（改名＝新技能，不是修改）；公共技能改公共仓（`.agents/skills/`，见 `references/spec-alignment.md`），不在私有目录另立副本
3. 第三步：先找既有条目改写（全局编辑纪律）——同类问题第二次出现，说明规则本身没写对，改写原条目而不是追加「注意 / 补充」；一个语义只存一处
4. 第四步：堵漏洞优于加条款——暴露的是某类判断缺失时，补判定规则与正反例，不给个例打补丁；连加三条针对性禁令仍压不住，换框架或加门禁
5. 第五步：重大修改（流程 / 输出格式 / 触发条件变了）后重跑真实提示词验证（同创建第九步）；小修只做执行路径自检
6. 第六步：执行路径自检（同「审查」第八步）

## 审查已有 Skill

**先分来源，再谈格式**：6 段结构与 ≤200 行只约束**自著 skill**。来源是 git / import / skillssh 的第三方说明书（例：manage-skills 属于 skills-manager 项目）**不改格式**——`skills update` 是整目录替换，补段落属于白改，下次更新就没了。真要改，前提是先 `skills set-source <skill> --local` 断开上游，而那是内容决策，先问用户。校验脚本对这一类报的缺失属误报：标注来源即可，不要为了过门禁去补段落。

1. 第一步：逐项对照 6 段结构，缺了哪段补哪段
2. 第二步：检查主文件行数 > 200 → 下沉到 references/
3. 第三步：检查是否有机械性验证仍靠 AI 脑补 → 改成脚本
4. 第四步：检查 Default stance 有核心原则 + 禁止行为
5. 第五步：检查 Workflow 是否用第一步/第二步…编号
6. 第六步：检查 Relative files 加载时机是否明确（读 vs 执行区分）
7. 第七步：报告缺失项，询问用户是否修复
8. 第八步（**执行路径自检**）：修改规则/格式/流程后，**假设自己现在接到该 Skill 对应的任务，会按修正后的规则执行吗**——沿执行路径走一遍：
   - 扫描全部「给 agent 看的指令位置」：SKILL.md 流程描述、references 规则文档、**脚本 docstring/注释**、自检清单——确认无旧规范残留（2026-08-09 教训：规则文档已改、脚本注释仍指导旧规范，未来执行会按旧规则做）
   - 模拟执行关键步骤：按修正后规则在脑中/只读方式推演一次任务，输出是否落在新规范内？**「模拟」= 纯推演，绝不真实落地任何操作**——尤其删除/移动/批量写入/修改文件等破坏性步骤，只推演路径与结果、不实际执行（如删除类规则只确认"规则指向哪、会删什么"，绝不真删；需要实证时用 dry-run/只读预扫，绝不直接执行破坏性命令）
   - 发现残留 → 立即修复，不留给下次

# Output format

| 段 | 必填 | 格式 |
|:---|:---|:---|
| YAML 门控 | 是 | name + description（含触发词和排除条件） |
| Default stance | 是 | 核心原则 + 禁止行为（各 ≥3 条） |
| Workflow | 是 | 第一步/第二步…编号，含决策点 |
| Output format | 是 | 字段名 + 类型 + 说明 |
| Relative files | 否 | 场景 → 文件映射表 |
| Source hierarchy | 否 | 优先级 1-4 列表 |
| 自检 | 是 | ≥3 条 checklist |

> 完整模板 → 见 `references/template.md`

# Relative files

| 场景 | 加载文件 | 内容 | 方式 |
|:---|:---|:---|:---|
| 查阅设计原则 / 写 description | `references/principles.md` | 八大原则详解（原则二含 description 写法细则与正反例） | 读取（消耗 Token） |
| 查阅工程规律 | `references/rules.md` | 工程规律 + 分层执行规则 | 读取 |
| 需要完整模板 | `references/template.md` | 6 段模板带注释 | 读取 |
| 判断 Skill 级别 | `references/levels.md` | 轻量/标准/重量 | 读取 |
| 需要示例 | `references/examples.md` | 正反例对比 | 读取 |
| 创建/重大修改后验证 | `references/testing.md` | 真实提示词验证流程（轻量/重量） | 读取 |
| 对齐开放规范 / 跨工具目录 / 安全 | `references/spec-alignment.md` | frontmatter 字段约束、渐进披露预算、目录对照 | 读取 |
| 机械验证/格式化 | `scripts/validate.py` 等 | 校验脚本 | **执行**（不读代码，看输出） |

> Reference = AI 读（类似翻附录），Script = AI 做（类似用量具测量）。区分的关键：计算结果精准 → 脚本；需要理解 → 参考文档。

# 自检

- [ ] YAML 门控：name + description（含触发词）？
- [ ] Default stance：核心原则 + 禁止行为各 ≥3 条？
- [ ] Workflow：第一步/第二步…编号？
- [ ] Output format：字段固定有类型？
- [ ] 主文件 ≤ 200 行？
- [ ] description 符合原则二细则（≤1024 字符、触发词前置、含负触发）？
- [ ] **真实提示词验证**：创建/重大修改后跑过应触发 + 不应触发测试？
- [ ] Relative files 加载时机明确（读 vs 执行标注清楚）？
- [ ] 机械性验证已改成脚本而非 AI 脑补？
- [ ] **执行路径自检**：修改后假设自己接到对应任务，会按修正后规则执行吗？（沿执行路径扫描 SKILL.md/references/脚本注释/自检清单，无旧规范残留；模拟执行=纯推演**不落地**，删除/移动/批量写入类操作绝不真实执行）？
