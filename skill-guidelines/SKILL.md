写给 agent 读的文档——一份 skill、`AGENTS.md` / `CLAUDE.md`、指针指向的任意一份 doc——packaging 各不相同，写法只有一套。agent 每轮跑的是同一个**过程**，不是产出同一个输出，所以目标不是"内容正确"，是**可预测**：同一句输入进来，走的是同一条路。

## 领词

六个词承载本 skill 的全部判断。正文只重复词，从不重述含义——重述含义就是沉淀。

| 领词 | 承载什么 |
|:---|:---|
| **指针** | 常驻上下文里、命名外部材料并写明到达条件的一句话。是**措辞**决定 agent 何时去取，不是材料本身。必备材料挂在弱指针后面＝一个 variance bug：先磨措辞，磨不动才内联 |
| **两种负载** | **上下文负载**＝每轮都占窗口的东西（description、`AGENTS.md` 的某一行），无论触发与否都付费。**心智负载**＝人得记住有哪些文档、何时取用。后者不是要最小化的成本，它是人类能动性的价格：该花在人判断上的就花 |
| **阶梯** | 一块材料放多深：① 正文步骤 ② 正文参考 ③ 指针后的独立文件。往下走那一步叫**渐进披露**——它首先不是省 token，是保护阶梯。放太浅顶楼臃肿，放太深藏掉 agent 要用的 |
| **沉淀** | 过期层因为"加着安全、删着风险"而堆积，直到你得钻过它们才找到还活着的部分 |
| **空转** | agent 本来就会照做的指令。判据是它改不改变得了行为——**相对模型，不相对读者**：两人对某句是否空转有分歧，就跑一遍定，不辩论。句子挂了整句删，别修剪字词 |
| **缓存** | 复述环境的文档（`package.json` scripts、config、目录布局、`--help`）。只缓存 agent 查不到的：未成文约定、选择背后的理由、config 不会招的坑 |

## Default stance

### 核心原则

- **一个 branch 一个触发条件。** 指针前置领词；同义词改写的是同一个 branch，就是一个 branch 写了两遍，合并。指针是每轮付费的那一行，比正文更该狠剪——身份若正文已承载，就从指针里删掉。
- **按 branch 切阶梯。** 每个 branch 都要的材料留正文，只有部分 branch 才碰的推到指针后面。**共置**：一个概念的定义、规则、坑收在同一标题下，读一处带出邻居。散（一个意义碎成很多处）与重（一个意义写在多处）是两种不同的病。
- **一步一判据。** 每个步骤止于**完成判据**，它有两个属性：**清晰**——agent 分得清做完与没做完吗？模糊边界招致提前收工，先收紧边界，只有边界确实不可约地模糊、且观察到抢跑，才把后续步骤藏到真实上下文边界之外；**强制**——"每条规则都已应用"逼出的苦功多于"产出一份变更清单"。最强的判据同时可核查且穷尽。
- **一个意义只存一处。** 改行为时是一处编辑。重复会把该意义的显著度抬过它在阶梯上的真实排名。唯一例外是领词：故意重复**词**，从不重复**意义**。
- **正向表述。** 靠禁令转向会把被禁行为拉进上下文，让它更**容易**出现而不是更难——说清要做什么（「写一行注释」），让被禁的那个不必被说出。无法正向表述的硬护栏才留禁令，且必须同时给出正向目标。
- **事前门禁 > 事后自检（2026-09-11 用户硬约束，最高优先）**：能靠 API / 脚本 / DOM 拦截的做成硬门禁，不合格数据根本写不进去；其次把检查点内嵌进 workflow 的判定步骤；再次给 ❌→✅ 对照表，让执行者动手前可比对；自检清单只兜底无法自动化的语义判断。
- **执行优于模拟**：机械性验证、计算、文件操作直接跑脚本，agent 不读代码只看输出。
- **逐句查相关性与空转。** 一行是否仍与文档要做的事有关？它会随行为或世界变化而变陈旧。没有修剪纪律时，默认归宿就是沉淀。
- **改动前先读。** 通读目标全文 + 相关 references + 脚本注释，定位旧规范残留。凭记忆改＝漏改。

### 边界

- 方法论与判断标准由人定义，模型只做格式化与补全。
- 输出即接口：字段名、类型、顺序固定。
- 规则要有来源；拿不准的标 `[待验证]`。
- 6 段结构与 ≤200 行只约束**自著 skill**。来源为 git / import / skillssh 的第三方说明书保持原格式——`skills update` 是整目录替换，补段落属于白改，下次更新就没了。校验脚本对这一类报的缺失是误报：标注来源即可。真要改，前提是先断开上游，而那是内容决策，先问用户。
- 公共仓库用 `$HOME` 相对路径，凭据只存本地 0600 文件或环境变量（细则见「AI 仓库公共化」）。

## Workflow

### 新建 skill

1. **定级** → `references/levels.md`。判据：级别已写下，且最少结构能由它推出。
2. **先写指针，再写正文**——指针决定材料会不会被取到。判据：每个 branch 恰好一个触发条件，正文已承载的身份描述不出现在 description 里。
3. **上阶梯**：步骤进正文，低频参考下沉 `references/`，机械校验进 `scripts/`。判据：正文 ≤200 行，且逐行过了相关性检查。
4. **填 6 段** → `references/template.md`。判据：必填段齐全；每个可选文件标明了加载时机（读 vs 执行）。
5. **跑真实提示词**：2–3 条带真实路径与口吻的提示词，应触发与不应触发各占一半，实际触发并复盘输出与 trace → `references/testing.md`。判据：两类各有至少一条跑过并留下结论。静态自检不替代这步——skill 的错误大多不在"写了什么"，而在"会不会触发、照不照做"。

### 修改已有 skill

1. **改前先读**（同上，通读而非凭记忆）。判据：能说出旧规范残留在哪几处。
2. **身份不动**：保留原 `name` 与目录名——改名是新技能，不是修改。
3. **先找既有条目改写。** 同类问题第二次出现，说明规则本身没写对：改写原条目，而不是追加「注意 / 补充」。
4. **堵漏洞优于加条款。** 暴露的是某类判断缺失时，补判定规则与正反例，不给个例打补丁。连加三条针对性禁令仍压不住，就换框架或加门禁。
5. **重大修改**（流程 / 输出格式 / 触发条件变了）后重跑第 5 步的真实提示词验证；小修只走下面的执行路径自检。
6. **执行路径自检**：假设自己现在接到该 skill 对应的任务，会按修正后的规则执行吗？沿执行路径扫一遍全部「给 agent 看的指令位置」——SKILL.md 流程描述、references 规则文档、脚本 docstring 与注释、自检清单——确认无旧规范残留（2026-08-09 教训：规则文档已改、脚本注释仍在指导旧规范）。判据：每一处位置都点过头。
   > 「模拟」＝纯推演，不真实落地任何操作。删除 / 移动 / 批量写入 / 改文件这类破坏性步骤只推演路径与结果；需要实证时用 dry-run 或只读预扫。

### 审查已有 skill

**先分来源，再谈格式**（见上方「边界」）。然后逐项走：

1. 6 段结构缺哪段补哪段。
2. 正文 >200 行 → 按 branch 下沉 `references/`。
3. 仍有机械性验证靠脑补 → 改成脚本。
4. Default stance 的核心原则与边界是否都在**正向**说话；禁令是否都能被正向改写。
5. 逐句跑**空转**测试与**相关性**检查；列出该整句删的行。
6. 找**重复**：同一意义出现在几处？留一处，其余改为指向它或换成领词。
7. 找**缓存**：复述环境可查的东西，删。
8. 每个步骤是否止于可核查且穷尽的**完成判据**。
9. description 里有没有同义重复的触发词、以及正文已承载的身份描述。
10. 报告缺失项，问用户是否修复。
11. 走一遍执行路径自检（同上）。

## Output format

| 段 | 必填 | 格式 |
|:---|:---|:---|
| YAML 指针 | 是 | `name` + `description`（一个 branch 一个触发条件，含负触发） |
| Default stance | 是 | 核心原则 + 边界，各 ≥3 条，以正向说话 |
| Workflow | 是 | 编号步骤，每步止于完成判据 |
| Output format | 是 | 字段名 + 类型 + 说明 |
| Relative files | 否 | 场景 → 文件映射，标明读 vs 执行 |
| Source hierarchy | 是 | 优先级列表，含「环境」这一层 |
| 自检 | 是 | ≥3 条，可核查且穷尽 |

> 完整模板带注释 → `references/template.md`

## Relative files

| 场景 | 文件 | 内容 | 方式 |
|:---|:---|:---|:---|
| 写 description / 查设计原则 | `references/principles.md` | 职责单一、指针写法细则、安全边界、级别与体量 | 读取 |
| 定默认行为 / 设计测试用例 / 中文专节 | `references/rules.md` | 未定项处理表、三类用例、递进建构 | 读取 |
| skill 专属机制（frontmatter、调用方式、路由 skill） | `references/mechanics.md` | model-invoked vs user-invoked 的取舍、按调用拆分、router | 读取 |
| 需要完整模板 | `references/template.md` | 6 段模板带注释 | 读取 |
| 判断级别 | `references/levels.md` | 轻量 / 标准 / 重量 | 读取 |
| 需要示例 | `references/examples.md` | 正反例对照 | 读取 |
| 创建 / 重大修改后验证 | `references/testing.md` | 真实提示词验证流程 | 读取 |
| 对齐开放规范 / 跨工具目录 / 安全 | `references/spec-alignment.md` | frontmatter 字段约束、披露预算、目录对照 | 读取 |
| 机械验证 / 格式化 | `scripts/validate.py` | 校验脚本 | **执行**（不读代码，看输出） |

> Reference 是 agent 读（翻附录），Script 是 agent 做（用量具测量）。分界：靠理解才能做对 → Reference；结果必须精密且不许出错 → Script。

## 自检

- [ ] YAML 指针：每个 branch 恰好一个触发条件？正文已承载的身份描述是否已从 description 移除？
- [ ] 逐句空转测试：有没有 agent 本来就会照做的指令？该整句删的删了吗？
- [ ] 相关性：每一行是否仍与文档要做的事有关？有无陈旧层（沉淀）？
- [ ] 单一来源：有无同一意义写在两处以上？重复处是否已改为指向那唯一一处？
- [ ] 正向表述：禁令是否都试过正向改写？留下的硬护栏有没有配正向目标？
- [ ] 完成判据：每个步骤是否止于**可核查且穷尽**的条件？有无"理解到位为止"这类模糊边界？
- [ ] 阶梯：正文 ≤200 行？只有部分 branch 才碰的材料是否已在指针之后？
- [ ] 缓存：有没有复述环境查得到的东西？
- [ ] 共置：同一概念的定义 / 规则 / 坑是否收在一个标题下，而非散落各处？
- [ ] 事前门禁：可自动化的校验做成门禁了吗，还是仍写成自检条目？
- [ ] 执行路径自检：假设自己接到对应任务，会按修正后规则执行吗？（沿路径扫 SKILL.md / references / 脚本注释 / 自检，无旧规范残留；破坏性步骤只推演不落地）
- [ ] 真实提示词验证：创建或重大修改后，应触发 + 不应触发各跑过至少一条？
