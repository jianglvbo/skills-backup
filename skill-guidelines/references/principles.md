# 设计原则细则

> `SKILL.md` 的「领词」表和 stance 已承载的判断（阶梯、共置、完成判据、单一来源、正向表述、空转、沉淀、缓存、执行优于模拟）这里**不再重述**。本份只放需要时才查的细节。

## 原则一：职责单一

一个 Skill = 一个明确的领域。复杂流程拆成多个 Skill 串联。

❌ 一个 Skill 同时处理行情、财报、博主
✅ 拆成 stock-analyzer、link-analysis、blogger-refine

## 原则二：指针怎么写

description 是 agent 选择 skill 的唯一依据，也是**每轮都付费**的那一行——它比正文更该狠剪。

- **前置领词**：指针是它做触发工作的地方，把最有辨识度的词放句首。部分客户端对技能列表有上下文预算（如 Codex 2%），超了先截 description。
- **一个 branch 一个触发条件。** 同义词改写的是同一个 branch，就是一个 branch 写了两遍——合并，只留真正不同的。「skill准则／skill设计／skill修改／skill规范／skill审查」是同一个 branch 写了五遍。
- **删掉正文已承载的身份描述。** 理念、定位、比喻属于正文；指针只回答"什么时候取用它"。
- **写意图不写实现。** 写「用户做什么时该用」，不写执行步骤——agent 匹配的是用户请求，且可能只看 description 就照做，步骤写进去会喧宾夺主。
- **宁 pushy 防 under-trigger**：模型普遍欠触发，显式列出适用场景，包括用户没点名领域时的说法。
- **一句排除条件**：写明不适用什么、与相邻 skill 的边界，压掉误触发。这是真正独立的 branch，不算同义重复。
- **长度 ≤1024 字符**（规范硬上限），两三句为宜。

❌ `帮助处理 PDF。`
❌ `触发词：「A」「A变体」「A的另一说法」「A的近义词」。`
✅ `提取 PDF 文本与表格、填表单、合并 PDF。处理 PDF 文档、表单或提到「抽取/合并文档」时使用；纯阅读 PDF 不用。`

调用方式（model-invoked vs user-invoked）的取舍见 `mechanics.md`——只有 user-invoked 的 skill 才该把 description 缩成一句话摘要。

## 原则三：确定性怎么落地

编号清单 > 自然语言。决策树 > if-else 描述。模板 > 自由格式。

散文式流程让每次跑的是不同过程；编号 + 判据把它钉成同一条路。

## 原则四：安全边界

限制工具范围，敏感数据只读，外部操作需确认。凭据放 `$HOME/.config/<skill>/`（0600）或环境变量，不进仓库。

## 原则五：Skill 级别与体量

判级见 `levels.md`。体量不是美德本身——短是为了让**相关性**检查做得动：一份 348 行的主文件里，判断"这一行还活着吗"的成本高到人倾向于不动它，那就是沉淀的成因。
