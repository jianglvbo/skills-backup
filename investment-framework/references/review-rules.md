# 审查规则

> 本文件是审查维度的唯一真相源。SKILL.md 的 workflow 引用此处定义，不重复描述。

## 复核建议处理（审查首步）

**每次审查开始前，先处理用户在「言论追踪」左滑写入的复核建议**（存于 MySQL `statement_review_sub`，子表 `_sub` 后缀）：

1. 调 MCP `console_statement_review(action=list, status=open)` 取出全部未处理建议（返回含建议正文 + 该言论当前 `contentType/stance/target/viewText` 上下文）。
2. 逐条按建议修正：用 `blogger_statement(action=update, id, contentType/stance/…)` 把归类改到用户要求；成功后 `console_statement_review(action=apply, statementId)` 置为已处理。
2b. **建议里出现「删除/删掉/不该录/不该落库」＝删除指令**（2026-09-12 用户明确：「有的帖子质量不够，但是你提炼了，这种我就会在复核意见写上删除」）：
    - 用 `blogger_statement(action=delete, id)` **真的删掉那条言论** → `console_statement_review(action=apply)`；**不要反问用户「确定要删吗」**（理由已给，删除已获授权）。
    - **必须内化**：把理由里的可泛化判据追加到 `refine-schema.md` 信息密度门槛的**「用户删过的类型」判据表**（理由原话 + 泛化判据 + 日期/言论 id），让同类帖子下次**不落库**——只删不内化＝下批继续犯（framework-rules #50）。
    - **同类一次判净**：按判据回看同批/存量里同类型的帖子，一并处理并汇报。
2c. **待决策页按 kind 分流（2026-09-27 用户拍板，取代「已决策的跟着提炼走、不跟审核」单向分工）**：提炼类条目（归类待定/时间存疑/标的解析等，含 `verdict=delete` 删除清单）仍由 `提炼环节` 第一步「1.1 清待决策队列」执行，审查不碰；**审查类条目（`kind=审查裁决`，由审查收尾步上报，见「审查发现上报待决策」）归审查闭环**——已答复未内化项在首步执行修复（第 5 点），未决项在收尾上报。
2d. **右滑删除记录**（2026-09-14 起用户在言论卡直接右滑删除）：suggestion 以 `【用户删除：无价值】` 开头，快照已入库（`类型｜日期｜正文摘要｜链接`），言论本体**已被看板删掉**（list 返回的 `post=null`）——不要再尝试 update/delete 该言论。处理＝**只内化**：从快照提炼可泛化判据（这类言论为什么留不住：闲聊无信号/纯复述/信息密度低…）→ 追加到 `references/refine-schema.md`「用户删过的类型」判据表（快照原话 + 泛化判据 + 日期/言论 id）→ `console_statement_review(action=apply)` 置已处理。只删不内化＝同类垃圾言论下批继续入库（#50）。
3. 若判断建议不成立（与 dict 判据冲突），`console_statement_review(action=delete, statementId)` 并在审查报告中说明理由，不静默丢弃。
4. **可泛化即固化**：凡某条复核暴露出通用规律，回写 `framework-rules.md #30` 的归类判据（观点/预测/研究…），让下次提炼自动遵循。典型例：`白酒处于底部（公募持仓全面退出为信号）` 属**当下判断 → 观点·看多(bullish)**，非预测（无未来时间窗/可验证目标位）——此判据已固化进 #30「易错判据（观点 vs 预测）」。

5. **执行已裁决的审查条目（2026-09-27 新增，审查首步必做）**：`pending_decision(action=list, kind=审查裁决)` 取已答复未内化项（`pending_internalize`）→ 逐条按用户答复执行修复（改库/改文件/迁移/删除；vault 内容级修改仅限该裁决授权的范围）→ `pending_decision(action=internalize, id, internalized="实际改动落点")` 关闭；执行明细写进审查报告「审查裁决执行」节。判断答复不成立 → `action=dismiss(id, reason)` 并在报告说明，不静默丢弃。

> 看板 UI 侧：原「待复核」badge 已移除，仅当存在复核记录时显示「复核」badge（tooltip 见建议原文）。

## 内容审查

检查框架内容质量：

| 审查维度 | 检查什么 |
|:---|:---|
| 内部一致性 | 交易体系的规则和分析框架的方法论是否矛盾 |
| 知行合一 | 投资心态里写的纪律，实际交易中是否遵守了 |
| 我的框架 vs 博主框架 | （可选，仅用户显式要求时）我的方法和博主的方法冲突时，标记出来让你判断——默认不审查「我的」层（规则 #15 用户自管） |
| 经验验证 | 投资心得里的教训，后续行为是否验证了 |
| 关联备注发现 | 为缺少跨条目关联的条目提议补充脚注（脚注类型和格式见 footnote-taxonomy.md），嵌入正文相关论述处 |
| 已存在脚注关系复核 | **复核文件中已有的每条关联脚注**：其关系声明（增强/补充/冲突/互补）必须有目标文件原文支撑；无依据的一律标记为"编撰关系"，建议删除或降级为 enhance（详见 footnote-taxonomy.md「关系依据校验」） |

产出：审查报告，标记冲突项和待确认项。

## 结构审查

检查框架文件的组织和规范：

| 审查维度 | 检查什么 |
|:---|:---|
| 归类正确性 | 文件是否放在正确的归属层（博主/其他）和分类下（「我的」层不审查，规则 #15 用户自管）。**迁移前必须反查入链**（check_inbound.py / grep）：入链落在「我的」层等不可修改层时**跳过迁移**并在报告说明，交用户处理（先例：2026-09-21 `仓位安全感三原则` 被我的层脚注指向故保留原位上报 → 2026-09-27 用户解除指向并裁决迁移（待决策 #51），已迁 `博主/令狐不败/交易体系/`、6 处入链改指——不可修改层阻碍解除后迁移即执行，不再无限期挂起） |
| frontmatter 完整性 | 通用必填字段（title/createDate/updateDate/**author**/tags/**source**）+ 模板特定字段是否齐全；**updateDate 与 author、source 为必填**，缺失即标记；**字段顺序须按所属分类模板 canonical 排列（framework-rules #27，标准 8 字段 `title→createDate→updateDate→author→star→delete→tags→source`，分析档案/宏观另有额外字段）**；**框架条目 frontmatter 禁止出现 `date` 字段（层间边界，framework-rules #27）** |
| 引号有效性 | frontmatter 中双引号包裹的值内部是否含未转义双引号（违反全局规则 #21） |
| wikilink 有效性 | **正文与 frontmatter `source` 字段**中的 wikilink 目标是否存在、双向互链是否完整 |
| 脚注格式 | 脚注定义中 wikilink 是否以单个 `]]` 闭合（禁止 `]]]` 或多余 `]]`）；格式是否为 `[[target]] — 关系：说明`（详见 footnote-taxonomy.md「格式校验」） |
| 分类标签 | 标签是否匹配实际内容 |

产出：问题清单，标注需要修正的文件和具体问题。

## 规律固化（审查收尾步）

每次审查收尾前，把本次**全部发现**（内容审查 + 结构审查 + 复核建议处理）强制二分——**禁止只修数据不留规则**，这是本框架自生长的唯一强制入口：

| 分类 | 处置 |
|:---|:---|
| 一次性数据问题 | 只修数据（改文件/改库），不留痕 |
| 可泛化规律 | **必须回写规范**，不允许「这次改了下次照犯」 |

**可泛化规律的回写去向**（按问题类型选，宁可多写一条规则也不留重复隐患）：

| 问题类型 | 回写位置 |
|:---|:---|
| 归类/判据类（如 观点vs预测、归属层、模板选型） | `framework-rules.md` 对应编号（#30 等） |
| 提炼执行类（漏字段、漏预检、顺序错误） | `references/refine.md` 对应步骤/硬约束 |
| 机器可检的结构类（格式/段落/wikilink/引用） | 操作门脚本加校验项（`verify-format.py` / `vault_review.py`）——**能脚本拦的不靠审查兜底**（framework-rules「操作门」原则） |
| 言论归类类 | 已由「复核建议处理」覆盖，同样回写 #30 |

**报告硬要求**：审查报告末尾必须有「规律固化」一节，列出——① 本次固化了什么（写明回写到哪个文件哪个条目）；② 哪些发现判定为一次性；③ 未固化的理由。**判定不了的按可泛化处理**。

> 先例（自生长靠收尾步强制，不靠下次记得）：2026-08-14 审查暴露 13 悬空引用/34 模板段落缺失 → 固化为操作门事前校验；同作者矛盾 → 固化为提炼预检；2026-09-06 白酒例 → 固化为 #30「易错判据（观点 vs 预测）」。

## 审查发现上报待决策（审查收尾步，2026-09-27 新增）

收尾时把**无法自行处置、需用户拍板**的发现上报 `pending_decision(action=add, kind=审查裁决)`——典型四类：C3 实质矛盾的互斥边界、历史数据的删除/保留、误挂条目的迁移去留、疑似重复/串号的归属。**机械可修的不上报**（授权范围内直接修），只报真正的裁决点。**疑似串号/归属不明先自证再上报**（2026-09-27 裁决 #50 用户教）：先用浏览器打开原帖 URL 验证博主归属，验得了就不上报、直接按事实修正；验不了才进队列——不把可自证的问题丢给用户。上报质量沿用 framework-rules #49：必带 `options`（`/` 分隔、选项文本内不得再出现 `/`）、`question` 一句话独立可懂、`excerpt` 放原文关键句；出处为 vault 条目时把相对路径写进 question/excerpt，statementId/sourceUrl 留空。已上报项由下轮审查首步闭环（本文件「复核建议处理」第 5 点），报告引条目 id 即可。

## 审查频率

由用户手动触发，或后续设定定期执行。**建议（2026-08-14 实践验证）**：
- **每周一次**结构审查（vault_review.py + verify-format.py 全自动，成本低）；
- **批量采集/提炼操作后**立即触发一次结构审查——2026-08-14 审查一次性暴露 13 处悬空引用、4 位未登记博主、29 处 info_cutoff 失同步、34 处模板段落缺失，均为操作后未即时校验累积而成；高频触发可避免问题堆积。
