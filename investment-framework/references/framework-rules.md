# 框架边界规则与全局规则

## 框架边界

### 投资心态 vs 投资心得
- 根因是情绪/心理的 → **心态**
- 能靠心态纪律避免的 → **心态**
- 其他有借鉴意义的经验教训 → **心得**
- **没有借鉴意义的直接丢弃**

### 分析框架 vs 交易体系
- 分析方法论、判断框架 → **分析框架**（工具箱）
- 具体买卖条件、执行规则 → **交易体系**（操作手册）
- 两者有交叉时允许交叉引用，各有侧重

### 分析框架内部：方法论 vs 分析档案
- **方法论**：分析方法本身（如"用PE判断企业是否值得买入"）
- **分析档案**：用这个方法论分析具体标的的实例（如"段永平用PE方法分析茅台"）
- 分析档案是方法论的应用案例，通过 wikilink 关联回方法论

## 全局规则

> **总纲·事前优先（2026-09-19）**：踩坑尽量在事前避免、不靠事后自检——能机器拦的一律做成写入门禁/判据（服务端强校验、`verify-format --preflight`、字段必填、行业表（wind）/`index_catalog`/封闭市场清单命中校验等），不靠"事后跑脚本补救 / 人读清单自查"；自检清单只留"无法自动化"的语义判断（归类取舍、信息密度、忠实度），不重述机器已拦的项；沿革与复盘（日期旁注、删了几行、备份路径、踩坑次数）不进正文、最多一行 `> 沿革：…`。判据错在别处就改门禁/改脚本，而非加一条"记得检查 X"。

1. 日期格式：原始资源用 `date`（帖子发布日期），框架条目用 `createDate`/`updateDate`（条目创建/更新日期），**均用 `yyyy-MM-dd` 裸写无引号**（Obsidian 才能识别为 Date 类型，可排序 / 做时间线 / Dataview 算间隔）；tags 中的日期同样用 `yyyy-MM-dd`。注：日期字段是唯一例外——即便其他值加双引号包裹，日期也必须裸写，否则退化为 Text 类型
2. 文件命名：中文，不带日期前缀
3. wikilink：完整路径 `[[目录/文件名]]`，不加 emoji
4. 模板文件统一放在 skill 的 `assets/` 目录（非 vault 内），vault 内不设模板目录
5. 框架是活文档，可持续修改迭代
6. 三大归属层（我的/博主/其他）各自包含完整的六大分类
7. 宏观双层存放：顶层 `宏观/` 存通用宏观框架与分析工具（如美林时钟、经济周期指标）；三大归属层下各自的 `宏观/` 子文件夹存该来源对具体宏观事件的分析。跨博主同一事件通过 frontmatter `event` 字段聚合（如 `event: 美联储加息周期`）
8. 行业不按市场分文件夹，用标签区分
9. 个股按市场（港股/A股/美股）分文件夹
10. 博主层按博主名字建子文件夹，档案文件放在该文件夹根目录，按需创建不预建空文件夹
11. 博主的分析框架下有方法论/和分析档案/两个子文件夹；我的和其他的分析框架下不设子文件夹。**博主层方法论条目必须放 `博主/{name}/分析框架/方法论/` 子目录，禁止直接放 `分析框架/` 根（2026-09-07 审查固化：7 条误放根目录，其中雪月霜《周期行业去产能…》因文件名含「行业」曾被 vault_review 模板误判为行业——根目录让模板判定依赖文件名猜测，一律归位子目录）**
12. 博主归类仅限博主控制台已登记的博主（登记权威 = 看板 MySQL `blogger` 表；vault 工作区/博主控制台.md 已于 2026-09-07 退役删除，勿再读写）。**粗加工/提炼时 Agent 严禁自动将新作者「补登」进博主控制台**——若原始资源 `author` 不在控制台，其框架条目一律归「其他」层（未登记投资人层），`author` 字段照实填写但不占用博主层路径、不建博主档案。**唯一例外**：post-fetch（已并入 xueqiu-spyder）前置步骤可从用户雪球关注列表同步新增博主到控制台（用户明确授权，见 xueqiu-spyder SKILL.md「前置同步」），同步时须向用户报告变动并确认。除此之外，任何情况下 Agent 不得自行新增博主。**删除走回收机制（2026-09-14 用户拍板，取代原「软删除沉底」）**：`remove_blogger` 置 `blogger.deleted_datetime` → 该博主**不再出现在博主菜单**，改列入**回收站**（与文件级 delete 同一套 7 天冷静期）。冷静期内 `restore_blogger` 随时可恢复；**满 7 天后 `purge_blogger` 回收**：① 把 `博主/<名>/**` 下的制品逐文件挪到「其他/<分类>/**」（重名加后缀，路径映射记入 `blogger_recycle_file`）；② 六张言论表里属于他的行 `del_flag=1` + `deleted_datetime=NOW()` 逻辑删除（`statement` 视图过滤，看板各处不再显示）。**恢复＝逆操作**：制品从「其他」搬回博主层、言论 `del_flag` 归零；同名重新登记（`add_blogger`）也会自动走这套还原。Agent 不得物理删除 blogger 行。
    - **`del_flag` 取值挂 dict**（`dict.type=del_flag`：`0`=未删除 / `1`=已删除），立卡在六张言论表上，与 `deleted_datetime` 成对使用。
    - **审查侧要排除已删除博主**：`/api/bloggers/live` 的每条带 `deleted` 字段；`vault_review.py` 的 `BLOGGERS` 只收 `registered && !deleted`——否则回收后挪到「其他」层的制品会被 `other_author_registered` 一直误报成「误挂」（见本条第 1 段的 #12 反例）。

    - **#12 反例（2026-09-07 审查固化，2026-09-09 恢复——03e9d8d 重构误删）**：其他层条目 `author` 若已是登记博主，属误挂——登记后应回迁博主层（历史案例：景风长赢 5 / 庶人哑士 2 / 七彩云龙 2 / 文主任 / 柯中 / 令狐不败等 15 条，多为登记前创建、登记后未回迁）。审查时 `vault_review.py` 反向校验 `other_author_registered` 提示；**登记/同步新博主后应顺带扫描该作者在「其他」层的既有条目并提请迁移**。甄别例外：解读/第三方整理某位大师思想（author 只是内容主角、非本人产出）不算误挂——「巴菲特谈投资」类以原文链接/背景为准人工裁决，勿机械迁移。
13. "其他"层只接收投资相关、来自具体投资人的内容；与投资无关的信息直接丢弃
14. 跨层查找靠 frontmatter 标签，不靠文件结构
15. "我的"层由用户自己管理，Agent 不维护
16. 没有借鉴意义的信息直接丢弃，不入库
17. Tags 规则：精简、分级、有用
    - 只加对分类检索有帮助的标签：行业、板块、市场（**不含个股名称**——个股标签只描述行业/市场特征，见 tag-taxonomy「实体描述原则」；个股名由文件名/标题承担，2026-08-08 用户纠正：华新建材裸标签违规）
    - **禁止方法论/内容性质标签**（基本面/价值投资/教训复盘/投资理念/交易系统/心态/仓位管理 等）——这些是内容主题不是分类维度，Agent 严禁"凭感觉"生成，必须从 `tag-taxonomy.md` 选定（2026-08-08 用户明确纠正：基本面/价值投资/教训复盘/投资理念等违规）
    - 禁止加无分类价值的标签（如 #RIO、#威士忌 等产品名/品牌名）
    - 用 "/" 做多级分级：行业/食品饮料/白酒、行业/食品饮料/葡萄酒、行业/AI与算力/AI应用
    - **禁止裸标签**（tag-taxonomy 层级硬约束）：标签必须挂在一级分类前缀下，最少二级（如 `市场/A股`）；个股文件 tags 示例：`[行业/食品饮料/白酒, 市场/A股]`（2026-08-08 修正：原示例含 `百润股份` 裸标签，与层级硬约束矛盾，已删）
    - 行业文件 tags 示例：[行业/农林牧渔/畜牧业, 市场/A股]
    - 宏观文件 tags 示例：[宏观/美联储, 宏观/货币政策, 2026-07-03]（2026-08-08 修正：原示例 `美联储/货币政策` 为裸标签，与 tag-taxonomy 宏观规则矛盾，已加前缀；日期标签保留裸格式）
    - **校验**：`vault_review.py` 应检测方法论标签违规（强化项，2026-08-08 提出）
18. 可读性优先：提炼产物要让读者快速理解、判断是否有用、记住核心观点。两个层面：
    - **修辞层面**：保留原文的比喻、案例、推理链条和生动表达，不做干巴巴的要点罗列。目标是让经验知识有"血肉"、可理解，而非只剩骨架
    - **认知锚点**（帮读者快速建立理解框架）：
      - **一句话核心判断**：正文开头用一句话浓缩全篇精髓，让读者3秒内决定要不要深读
      - **适用条件/边界**：显式标出这个经验在什么条件下成立、什么条件下不成立。没有边界的经验等于鸡汤
      - **反直觉点**：如果原文有"大家以为X，其实是Y"的认知冲突，在开头把张力拎出来
      - **时间敏感性**：标注经验产生的市场环境和时间背景，帮助读者判断是否还适用
19. 忠实原文：可以重组表达、优化结构、补充上下文说明，但绝不捏造、编撰、偏离原文事实。比喻和案例必须来自原文或原文引用的真实来源
20. 脚注体系：三类脚注（关联/数据溯源/时效标注），定义、格式、添加阶段和位置详见 `footnote-taxonomy.md`。提炼阶段可加 `[^data-N]`（数据溯源）和 `[^date-N]`（时效标注）；关联脚注（enhance/supplement/conflict/complement/opposite）仅在审查阶段添加。**提炼阶段文件不含 `## 关联` 章节，也不含空脚注占位**（关联脚注在审查阶段随文末脚注定义一起写入；脚注定义放文末、**无 `## 脚注` 标题、无 `---` 分隔线**——Obsidian 阅读模式自动渲染脚注分割线，手动 `---` 会重复，2026-08-09 用户确认）。**脚注 wikilink 目标仅限 wiki 产物**（`我的/`、`博主/`、`其他/`、`宏观/` 下的框架条目或博主档案），**禁止指向 `工作区/` 下任何文件**（原始资源/粗制品/控制台等）；data 脚注来源写纯文本描述、不用 wikilink，原始资源溯源由 `source` 字段承担（详见 footnote-taxonomy.md 禁止行为 #6）。**`opposite`（对立）标签**（2026-08-08 新增）：用于观点/操作规则**直接对立**的关联（非此即彼、行动相反），与 `conflict`（有张力可调和）区分，判据见 footnote-taxonomy.md「冲突 vs 对立」。
21. Frontmatter 引号规则：YAML 值的外层包裹必须根据值内引号情况切换，否则 Obsidian Properties 面板解析异常：
    - 值不含引号 → 双引号包裹：`title: "珀莱雅深度拆解"`
    - 值含双引号 → 单引号包裹：`title: '周期股投资的"债券+期权"思维'`
    - 值含单引号 → 双引号包裹：`title: "错过'时代'是最大的风险"`
    - 值同时含双引号和单引号 → 双引号包裹+转义：`title: "他说\"好\"了"`
    - **禁止**：双引号包裹的值内部出现未转义的双引号（如 `title: "理解"书""`）
22. 提炼输入必须是原始资源且 `status=待提炼`：提炼环节的输入必须来自 `工作区/原始资源/` 中 `status=待提炼` 的文档，**禁止**直接在 `工作区/粗制品/` 上提炼。判断以**原始资源为锚点**——若原始资源中不存在该文档的 `status=待提炼` 记录，说明仍在粗制品，编排者须先走粗加工环节（references/coarse.md） 完成粗加工（置 `status=待提炼`），再进入提炼。
23. `source` 字段（框架条目与原始资源）：YAML 数组，每项须引号包裹，**二选一形态**——内部来源用 wikilink，外部来源用 markdown 链接。**多个来源统一写入 `source`，框架条目正文不再设 `## 来源` 段落**（与正文 `## 来源` 段落二选一，现统一用 `source` 数组）。
    - **链式引用约定（2026-08-08 用户确认）**：**wiki 文件（框架条目）的 `source` 一律指向原始资源 wikilink** `[[工作区/原始资源/{文件名}]]`；**原始资源的 `source` 再指向真实 URL**（markdown 链接）。两级链式溯源——wiki 层不直接写 URL。**例外（无中间层直投）**：博主言论直接提炼（#29 帖子集路径）与截图/链接直投（#30 路径，**无原始资源中间层**）时，框架条目 `source` 可直接指向真实 URL——**没有原始资源可指向，URL 是唯一可溯源写法**（2026-08-08 用户确认：如「后视偏差」条目 source 直接写公众号 URL 属正确形态、非违规；审查时不得判为 `source_as_invalid`）。
    - **内部来源**（本库文档，如 `工作区/原始资源/` 下文件）→ wikilink：`"[[工作区/原始资源/{文件名}]]"`，可双向追溯、审查反查。
    - **外部来源**（雪球/公众号/网页/抖音等）→ markdown 链接：`"[{标题}（{作者} {YYYY-MM-DD}）]({真实URL})"`，URL 必填真实原文链接（雪球帖/公众号原文），**禁止用采集批次名**（批次提炼后即删，会成悬空引用，呼应 #96）。
    - **决策树**：来源是本库文件？→ wikilink；是外部链接？→ markdown 链接；两者都不是 → 报错。
    - **粗加工提取规则**：粗制品 frontmatter 的 `url` 字段（笔记同步助手/插件写入的原始链接）是原始资源 source 的来源，粗加工时必须提取（见 粗加工环节 第五步B）。
    - **禁止**：裸 URL（`source: "https://..."` 单行或 `- "https://..."` 数组项）、`[标题](相对路径)`、采集批次名、渠道名占位（如 `"AI整理 - 抖音"`、`"雪球长文"`）。链接文字禁止留空、禁止用超长脏 title（以文件名或简洁标题为准）。
    - 多条来源按「先内部后外部」排列；无来源则该字段留空数组 `source: []`，不加占位演示行。
    - 校验：`vault_review.py` 检测非法形态标 `source_as_invalid`；审查（结构审查）复核每条 source 形态符合本规则。
24. 繁体转简体：粗制品若为繁体中文，入库的原始资源（含正文）必须转为简体中文；提炼产出的框架条目正文同样使用简体中文。仅做繁简字形转换，**保留原文用词、语气、比喻、案例、推理链条，不改写内容**。粗加工阶段是转换的主责环节（粗加工环节）；提炼阶段（提炼环节）若发现原始资源仍为繁体，作兜底转换。

25. 删除原始资源须连带清理产物与引用痕迹：删除 `工作区/原始资源/` 中某文档时，必须一并清理其所有提炼产物与引用痕迹，保持 vault 无悬空 wikilink / 脚注。**执行前置（2026-08-14 强化）**：删除/回收/移动任何 wiki 条目或原始资源前，**必须**先运行 `scripts/check_inbound.py {VAULT_ROOT} <目标路径>` 反查全部 inbound 引用（wikilink / 关联脚注 / source 字段），按清单逐处清理后才允许删除——未跑反查不得删除（2026-08-14 教训：段永平 7 文件删除未反查，遗留 11 处悬空脚注直至审查才暴露）：
    - 删除该原始资源对应的**所有框架条目**（提炼产物文件，一篇可拆多条故可能多个）；
    - 产物内定义的脚注（文末脚注区的 `[^x]` 定义 + 正文中的引用标记 `[^x]`）随文件删除一并清除；
    - vault 内**其他正文**（含博主档案、其他条目）中指向这些产物的 wikilink、关联脚注引用标记（`[^x]: ... [[产物]]` 类）全部清除；
    - **博主层特例**：若被删产物归属层为博主层，且被删的是该博主**最后一个产物**，则连同 `博主/<名>/` 目录一并回收；若该博主仍保留有其他产物，则只清理产物本身与指向它的引用（**画像 md 已于 2026-09-14 清空，不再有「档案骨架」需要保留**，见 #36）。

26. 待删除标记与 7 天冷静期回收（delete 字段机制）：框架条目若你觉得质量不佳需回收，**在条目 frontmatter 的 `delete` 字段填标记日期**（`delete: {YYYY-MM-DD}`，值 = 标记当天日期，Obsidian Properties 选 date 类型）。**`delete` 为内容型条目常驻字段（2026-08-05 起全条目含之），缺省空值 = 未标记**；空值不参与回收判定。**无独立回收控制台**（2026-08-05 已废弃表格控制台与历史记录文件）：
   - **字段类型注册（重要）**：`delete` 的 Date 类型依赖 vault `.obsidian/types.json` 注册（`"delete": "date"`，与 `"star": "checkbox"` 同级）。**若该文件缺失/被重置，空值 delete 会被 Obsidian 当 Text 处理**——新建/迁移 vault 时必须保留 types.json 的这两项注册，否则属性类型语义丢失（star 变文本开关、delete 失去日历选择器）。
   - **标记**：`delete: 2026-08-05` 即标记该条待回收。**标记操作由用户手动执行**（在 Properties 面板填日期），Agent 不替用户标记。
   - **撤销 = 清空字段**：标记日期起 7 天内，你随时清空 `delete` 字段（恢复空值）即可撤销回收，无任何副作用，条目保持原样。

27. 层间 frontmatter 字段集边界（防提炼误带字段）：框架条目层与原始资源层使用**不同的 frontmatter 字段集**，提炼时只搬运语义对应的字段，绝不可把原始资源的字段整体照搬进条目：

   - **框架条目层**（提炼产出，落各分类模板）字段集：各分类模板定义者——`title` / `createDate` / `updateDate` / `author` / `star` / `delete` / `tags` / `source` + 分析档案额外 `标的` / `status` + 宏观额外 `event` / `时效状态` / `时间范围`。

   - **硬约束**：框架条目 frontmatter **禁止出现 `date` 字段**（那是原始资源层的发布日字段）；提炼从原始资源生成条目时，仅取 `author` / `source` 等语义对应字段，**绝不把原始资源的 `date` 带入条目**——否则会在条目层制造"流浪 date"，破坏 frontmatter 规范（呼应 #1 日期格式约定）。
   - **字段顺序（canonical）硬约束**：框架条目 frontmatter 字段必须按所属分类模板的 canonical 顺序排列（各 `assets/*.md` 模板即唯一真相源）。标准 8 字段顺序：`title → createDate → updateDate → author → star → delete → tags → source`；分析档案：`title → 标的 → createDate → updateDate → author → star → delete → status → tags → source`；宏观事件型：`title → event → 时效状态 → 时间范围 → createDate → updateDate → author → star → delete → tags → source`。**禁止打乱顺序**（如 `source` 前置、`tags` 置底）。审查（审查环节 S3）与 `vault_review.py` 据此检测顺序漂移。
   - **`author` 必填**：每个框架条目必须有 `author`——wikilink 来源从原始资源取博主名；外部 URL 来源填原出处，无则填 `待补`。提炼产出条目若漏 `author` 视为 frontmatter 不完整（与审查自检联动）。
   - **`id` 字段豁免（2026-08-04 新增）**：`id`（形如 `id: docid_xxx_e`）是 Obsidian 第三方插件（如 Visit History 等阅读追踪类插件）写入的文档追踪 ID，**不属于框架字段集，不参与 canonical 顺序校验，不参与必填/缺失/引号检查**。提炼、粗加工、审查、格式校验（vault_review.py / verify-format.py）遇到 `id` 字段时**一律忽略**——不得删除、不得移动、不得报错。frontmatter 解析按"id 为外部字段"处理。

32. 微信/IM 截图与链接输入流程：用户通过微信/IM 发送博主截图或雪球链接，Agent 按以下流程处理：
    - **输入形式处理**：
        - 单张截图 → 从图片内容识别博主和内容；
        - ~10s 内连续多张截图 → 视为同一帖子的分段截图，**合并为一条**处理，不拆成独立条目；
        - 雪球链接 → 用**浏览器**打开读取（WebFetch/curl 会被雪球反爬拦截），提取正文和评论区作者回复；
        - 截图 + 链接 → 以截图内容为主，链接补充原文链接字段。
    - **识别博主**：优先从截图内容（昵称/头像/上下文）推断博主身份，查看板博主控制台（MySQL blogger 表，GET /api/bloggers/live）确认登记状态；无法确定时询问用户。
        - 已登记但 `blogger` 表无行 → `add_blogger` 建 DB 行即可（summary/strengths/limitations 可空），不询问用户；**不建画像 md**（2026-09-08 画像单轨化）；
        - 未登记 → 归「其他」层，**不补登、不询问**（见 #12）。
    - **原文链接必填**：截图输入时若用户未提供原文链接，**主动提醒用户补链接**，不默默用 `-` 占位。
    - **分析内容 → 路由落地**：
        - 涉及买卖动作（买/加/减/卖/清仓）→ **必须**经 `blogger_trade` 落买卖帖言论行 `statement_trade`（见 #31），同时实时抓取价格/市值填入；买卖的价格取值和备注规则见 #31 硬规则；
        - 个股/行业观点（非动作）→ 言论库对应类型表（`statement_view` 观点 / `statement_research` 研究 / `statement_predict` 预测…），分类权威＝`content_type`；
        - 有框架价值的行业/方法论洞察 → 走提炼环节（references/refine.md） 提炼为独立框架条目；
        - 方法论/心态/体系类 → 按常规提炼流程归入对应分类。
    - **选择性落地**：无借鉴价值的纯调侃/碎碎念不入库，告知用户已跳过。
    - **买卖必录**：只要识别出买卖动作，无论内容是否有其他价值，买卖帖必须落地。
    - **更新博主档案**：录入后更新 frontmatter 的 `updateDate` 和 `info_cutoff_datetime`（ISO 时间格式 `YYYY-MM-DDTHH:mm:ss`，默认当天 `17:50:00`，采集后按实际完成时间更新，见 #36）；如内容被提炼为框架条目，在言论追踪信号列标注 `已提炼为框架条目[[条目名]]`。

33. 段落布局：框架条目正文须遵守以下排版约束（审查结构维度之一，verify-format.py 自动检测）：
    - **标题前后空行**：`##` / `###` 标题行前后各有一个空行（文件首行标题除外）；
    - **段落间空行**：不同论点/维度之间用一个空行分隔，不紧凑堆叠；
    - **禁止同行标题**：`##` / `###` 不得嵌在段落末尾同一行（如 `正文。## 标题`），否则 Obsidian 不渲染为标题；
    - **连续行数上限**：连续 ≥5 行无空行视为段落过于紧凑，需拆分。

34. 脚注内联标记成对：脚注定义（文末脚注区的 `[^x]: ...`，无 `## 脚注` 标题、无 `---` 分隔线）与正文内联标记（`[^x]`）必须成对出现，禁止孤儿脚注（审查结构维度之一，verify-format.py 自动检测）：
    - **有定义无标记**：文末有 `[^enhance-1]: ...` 但正文中找不到 `[^enhance-1]` → 孤儿定义，需补内联标记或删除定义；
    - **有标记无定义**：正文中出现 `[^data-1]` 但文末脚注区无对应定义 → 悬空标记，需补定义或删标记；
    - 脚注描述必须有信息量，禁止"A与B的跨维度关联"等模板废话。

43. 批量数据修复脚本纪律（2026-09-11 教训：一个脚本写坏 50 行正文与回应）：言论表的批量修复**比新建更危险**——新建写错只影响新数据，修复写错会覆盖已经正确的历史行。凡对 `statement_*` 做批量 UPDATE 的脚本，必须满足：
    - **只改目标字段**：修 `reply_to` 的脚本**不得顺带覆写 `view_text`**。本轮脚本想「顺手把正文也补全」，结果把采集文件原文（含 `## N.` 标题行、`> 发布：` 行、重复片段）写进正文，50 行被污染（`view_text LIKE '## %'` 是它的指纹）。
    - **段落切分终点必须从本贴标题往后找**：从采集文件取某帖正文时用 `t.indexOf('\n> 发布：', 标题位置)`，**不能从 URL 位置往后找**——URL 就在本贴的发布行里，从它往后找会抓到**下一篇**的发布行，把 `> 发布：…` 和下一篇内容一起吞进来（本轮 `reply_to` 里的 `> 发布：…` 就是这么来的）。
    - **先 dry-run，且打印「旧值 → 新值」**：只统计条数不够，必须能逐条肉眼核对（本轮 dry-run 输出 `新正文: (无源JSON)` 时就该停下来查源，而不是继续跑）。
    - **落库后特征串复检**：修复完必须查 `view_text LIKE '## %'`、`reply_to LIKE '%发布：%'`、`LIKE '%回复@%'`、`LIKE '%已提炼见%'` 等污染指纹，全部为 0 才算修完。
    - **优先还原而非就地清洗**：能从落库源（子任务 JSON / load 脚本 / backups）取回原值的，一律还原；就地正则清洗只作为兜底。
    - **可回滚**：动手前留快照（`SELECT ... INTO OUTFILE` 或 JSON dump 到 `backups/`），写明删除/修改原因。
    - **文件侧批量改写同样适用本条**（2026-09-28 教训：一次 wikilink 改指把 6 文件 9 处打坏）：wikilink/引用批量替换**禁用含 `[` 的裸 sed 正则**——BRE 把 `[[...]]` 解析成字符类，`s|[[A]]|[[B]]|g` 实际匹配「类内单字符+`]`」（如 `则]``系]``仓]`），会把文件里所有此类位置替换成新串。一律用 python `str.replace` 字面替换并逐处断言出现次数；改完必须跑 `vault_review.py`（wikilink_issues/footnote_format/source_as_invalid 三键）+ git diff 逐行核对归属。
